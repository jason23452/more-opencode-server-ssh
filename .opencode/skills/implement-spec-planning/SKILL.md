# 限時可運行範圍規劃

有指定時間時，以該時間為預算選取可運行 TODO；未指定時間時，依指定 spec／tickets 的未完成範圍主動估算所需時間與分批排程。兩種模式都要完成多 Agent 分析，選擇整體經過時間最短的可行方法。規劃與實作分開：本流程完成規劃文件的核對與 commit 後即停止，不呼叫 `question`、派實作 Agent、建立實作 worktree、修改程式或啟動服務。

授權、文件提交與後續實作規則以根目錄 `AGENTS.md` 為準。`to-tickets` 建立並核對 tickets 與索引後自動銜接本流程；實作中僅引用第 6 節時，不重新執行規劃提交與停止流程。

## 1. 確認時間與候選工作

- 續作時核對各來源 worktree 的 `pr/` 待合併報告，區分尚未實作與已交付但未進入 `dev` 的成果。後者不重排實作，必要依賴未合併時列為阻礙，交由使用者另行呼叫 `merge-worktrees`。預定分支、worktree 及報告使用批次識別避免撞名。
- 先讀取 `docs/agents/issue-tracker.md`，再讀 spec、tickets 與依賴；探索程式碼前讀取 `docs/agents/domain.md`。記錄基準 SHA、規劃開始時間及時區。
- 「實作 N 分鐘」指後續獲准開始實作起的預算，規劃耗時另記；固定交付時間使用絕對時間；明示包含規劃的總時長從本輪規劃開始計算。普通時長預設為實作預算，明確寫出此解讀。
- 指定時長預設規劃限時批次，包含必要驗證、PR 報告、紀錄與已整合 ticket 資源清理的預留；合併 `dev` 與來源整合 worktree 清理由後續 `merge-worktrees` 另行執行及計時。明確要求完成本批所有選項才採完成導向，明確不得超時則採硬截止。每批以完整可運行切片交付，時間不足的未完成切片留到下一批。
- 未指定時間時採「估時規劃」：讀取指定 spec 及全部相關 tickets，盤點剩餘 TODO 與依賴，執行四職責分析，提出完整候選範圍、建議首批可運行切片、各批時間區間、關鍵路徑及收尾預留。估計標為 Agent 預測，不當作使用者預算；狀態為「估時完成／待確認時間」。單純缺少時間不是停止分析的理由。只有 spec／ticket 無法定位或具體歧義阻擋分析時，才記錄輸入不足；可分析範圍仍先完成。
- 時間確認門檻：估時提案提交後停止；使用者後續明確採用建議批次及時間、提供自己的預算，或確認指定範圍採完成導向後，才可轉為可執行計畫。若只是再次呼叫 `implement-spec` 而時間模式仍未確認，透過 `question` 提供既有估時與批次選項，不重做同一分析。新預算導致範圍／排程實質變更時，更新規劃並提交後停止。
- 以 ticket 路徑及 TODO 標題／子項文字識別候選工作；以目前內容核對未完成狀態，區分工作 TODO 與尚未勾選的驗收條件。已完成項目只核對可重用證據，不重新排入實作。
- 續作先讀最新 `dev` 的批次交付與合併紀錄。已合併且清理的批次視為已結束，仍未完成的功能、待補驗收與新階段 TODO 統一納入候選。明示待使用者安排的測試保持暫緩，記錄是否真正阻擋候選切片；新階段可規劃但不因而取得實作授權。新批次使用新預算或仍有效的待執行計畫，未提供預算則重新估算剩餘範圍，不沿用舊批已耗盡的時間。
- 依使用者明示優先級、既有票單優先級、依賴解鎖價值及可操作流程價值排序；無明示優先級時，列出採用依據。讀取全部 tickets 是為了核對依賴，不代表本輪實作全部 tickets。

完成條件：候選項目、時間來源、基準與阻礙可追溯；事實、估計及未知條件分開標示。

## 2. 多 Agent 尋找高效率方案

首次規劃預設啟動四個唯讀 subagents，以背景模式平行分析；每位提供相同的時間預算（未指定則明示「估時規劃，請估算所需時間」）、基準 SHA、spec／ticket 路徑、規範入口及候選範圍，各自回報下列證據：

| 職責 | 交付內容 |
|---|---|
| 重用與最小修改 | 既有 API、元件、測試與相關符號，最少必要修改位置、相容性及可行替代方法 |
| 優先級、依賴與分工 | TODO 的必要依賴閉包、可獨立交付組合、關鍵路徑、共享檔案所有權及並行安排 |
| 整合與運行環境 | 啟動前置、資料／遷移、服務連線、整合節點、實際可操作流程及環境阻礙 |
| 驗收與時間可行性 | TODO 對應驗收、真實運行驗證、必要測試與 review、修正預留、耗時依據及遺漏風險 |

- 規劃 Agent 只讀取並回報，不修改檔案、Git 狀態或啟動服務。命令與測試分為「已有執行證據」及「建議後續執行」。
- 主 Agent 比較有實質差異的候選方法，包括重用、分工與整合成本；以相同範圍及資源假設比較經過時間，不能把縮小範圍宣稱為方法更快。先滿足優先級與可運行門檻，再比較交付效率。
- 並行上限不足時分批；無法委派時標記「多 Agent 分析未完成」，保留暫定規劃與限制，不宣稱已完成最佳方案比較。已有有效分析只補查變動部分。
- Agent 啟動、上下文、工具等待與彙整成本須納入相應階段；Agent 數量不等於效率。規劃採多 Agent，實作並行數則依衝突、資源及實測效益決定。
- 回報來源用職責名稱、檔案及 SHA；未獨立核對的結論標記「依回報摘要，未獨立核對」，不寫入工具 session ID。

完成條件：四個職責均有證據或明確限制，分歧已核對，選用方案的優勢與代價可查證。

## 3. 選擇可真正運行的交付範圍

1. 由高優先級 TODO 組成端到端交付切片：具備實際入口、核心行為、必要資料／服務及可觀察結果；依功能性質選擇 UI、API、CLI 或其他真實入口。
2. 補齊所有未完成的必要依賴與不可拆分驗收。依賴不在候選 TODO 時明列來源及所需工作，不能當作已完成或隱藏成本；需求／授權不明則標記受阻。
3. 預算包含後續探索、環境準備、實作、worktree／交接、整合、測試、review、修正、checklist、session notes、PR 報告及已整合 ticket 資源清理。來源整合 worktree 保留待選擇合併，後續 `merge-worktrees` 耗時另計。依據既有實測或具體假設估算區間，列出停止新增工作的收尾時間點，避免用單一人類串行工時或 Agent 工時總和代替經過時間。
4. 以依賴與資源約束排共同時間軸。平行工作以匯合後的關鍵路徑計算，納入共享檔案、串行合併及資源等待；依風險保留修正時間並說明理由。
5. 預估放不進預算時，先改善重用與分工，再移除低優先級的完整切片；保留依賴閉包與必要驗證，列明未選 TODO 與理由。部分 ticket 可入選，但未選項目不代表取消，也不將整張票標記完成。

### 時限可行性與不足回報

有預算時列出預算、可用時間、關鍵路徑、估計上下界、依據與差額。最小可運行流程仍超出預算時，提交「預算內不可行」計畫，列出最低範圍、預估所需時間與瓶頸後停止。估時規劃則列出完整候選範圍與建議首批的時間區間、假設、信心及瓶頸，預算差額標為不適用；同樣預留必要驗收、review、PR 報告及交接收尾時間。

相對實作預算以後續啟動為零點；固定期限與包含規劃的總時長須扣除已經過時間，提交前再次核算。估計是有依據的預測，不保證未知成本；接近上界或存在外部阻礙時明列風險。

完成條件：選定範圍具有完整運行路徑、依賴與驗收，預算可行性有依據；或清楚記錄無可行範圍的原因。

## 4. 寫入可直接交接的計畫

沿用該 spec 既有規劃文件；沒有時使用 `.scratch/<spec-slug>/implementation-plan.md`，避免另建重複追蹤文件。目標 spec 無法辨識時，使用 `planning/implementation-plan-<YYYYMMDD-HHmmss>.md` 保存輸入不足紀錄。依 repo 的文件規則確認路徑可追蹤；被忽略時回報阻礙，不擅自強制加入 Git。

計畫必須包含：

- 時間來源（使用者預算或 Agent 估算）、計時口徑、規劃耗時、基準 SHA、計畫狀態（可執行／估時完成待確認時間／輸入不足／不可行／分析未完成）。
- 批次識別、前批合併 SHA 與未完成項的承接、時間模式、收尾預留、可獨立交付切片及其合併門檻。不得覆寫前批交付歷史來假裝它尚未開始。
- 本輪可運行成果、選入及未選 TODO、理由、不可拆分依賴與驗收對照。
- 四職責來源摘要、候選方法比較、選定理由、可用並行數、關鍵路徑與估算信心。
- 以下排程及交接表；分支與 worktree 只列預定名稱，不建立。

| Ticket／TODO 子項 | 依賴與修改範圍 | Agent／預定分支與 worktree | 相對開始–完成 | 驗收、review 與運行證據 |
|---|---|---|---|---|
| 路徑及子項 | 必要前置、共享契約與檔案所有權 | 實際可用資源 | 含整合及驗證成本 | 指令、環境與預期結果 |

- 可重用檔案／符號、必要修改位置、共享 API 契約、整合檢查點與首個可驗證成果。
- 真實運行驗收：安裝／啟動指令、環境變數名稱、資料前置、健康檢查、實際操作及預期結果、證據保存方式。涉及資料保存時涵蓋寫入及讀回；涉及外部服務時列明可用條件及驗證限制。
- 已有證據的 SHA 與覆蓋範圍、待執行檢查、假設、阻礙與下一個校正點。規劃中的命令不算已通過；僅編譯、單元測試或 mock 不足以證明實際流程可運行。

完成條件：後續 Agent 能依計畫直接定位範圍、啟動方式及驗收要求；規劃不修改原 ticket 狀態或 checklist。

## 5. 核對、提交並停止

1. 核對內容、相對連結、TODO 追溯、依賴閉包、時間計算、運行驗收與變更範圍；確認沒有把預測寫成已驗證結果。
2. 檢查 Git diff 及暫存區，只提交本輪核對的規劃文件，使用繁體中文提交訊息。保留既有及其他工作區變更；如同一文件含無法分離的既有變更，保留文件並回報提交阻礙。
3. 依 `AGENTS.md` 的規劃文件自動提交例外直接 commit，不呼叫 `question`。commit 失敗時保留成果並明列原因，不能宣稱已提交。
4. 回報計畫路徑、選入範圍、預估時間、限制及 commit SHA，立即結束。計畫提交不等於實作授權；後續由使用者另行要求實作。

完成條件：規劃已核對並提交，或已明列未提交阻礙；本輪沒有實作副作用或開工確認提問。

## 6. 後續實作引用：增量排程與風險審查

本節只供已獲授權的 `implement-spec` 引用；啟動授權與時間模式依 `AGENTS.md`。原計畫所選 TODO 是本批目標，限時收尾時以實際可交付切片記錄成果及差異，不要求整份 spec 完成。

- 實作 Agent 核對計畫版本與基準，只補查缺漏及變動部分。所有 Agent 共用開始時間、目標與時間模式；切換 ticket、重試或重排不重設計時。
- 在前置整合、驗證失敗或資源變動影響交付時，只更新受影響排程，回報「變動與證據 → 受影響工作 → 新分工 → 預計交付時間」。時間不足回報沿用第 3 節格式；限時批次把未完成切片及其驗收移至下批，明列差異並保留需求，不能把已交付切片的必要驗收省略。延長實作時間須依 `AGENTS.md` 取得授權。
- 首個端到端流程及高風險介面整合後即執行必要驗證；實際啟動並操作計畫指定流程，保存版本、指令、結果與覆蓋範圍。無法運行時記錄阻礙，不能宣稱本輪完成。
- 呼叫 `code-review` 的 `implement-spec` 模式，提供固定基準／待審查 SHA、選定 TODO 與驗收、適用規範、既有證據、剩餘時間及風險。Standards 與 Spec 兩軸均須覆蓋必要範圍；Spec 軸依本輪範圍檢查，也核對其與整體 spec 的相容性。
- 必修問題包含需求缺漏、行為錯誤、硬性規範違反及有證據的重大風險；每項附位置、依據、影響及驗證方式。命名偏好、推測性 code smell 或範圍外重構列為非阻擋建議。
- 修正後只複查差異及受影響範圍；版本與範圍仍有效的證據直接重用。必要檢查未完成時維持未完成，不以配額耗盡視為通過。
- 只勾選已實作且驗證的項目；批次結束、待合併、成果已合併與 ticket／spec 驗收完成分開回報。本批可交付成果使用 `pr` 保存 repo 內報告，保留來源整合 worktree／分支，交由使用者另行呼叫 `merge-worktrees` 多選合併；開發收尾不詢問或執行合併 `dev`。剩餘工作留給下一批；延後驗收項仍標記待補，不能因合併而視為驗證通過。
